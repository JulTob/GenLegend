## 🔍 Diagnosis (what & where)

Found while moving GenLegend from TagKit 0.2.0a1 to TopKit 0.2.0a3 (2026-09-24). Each was reproduced on 0.2.0a3 and on upstream `main` (0.2.0a4, `c615761`).

### 1. A `@Flag` applied after any non-Flag Tag never answers by name

```python
@Flag
class Undead(Tag): pass
class Player(Tag): pass

c = Char(); Player(c); Undead(c)
"Undead" in c          # TypeError: argument of type 'Char' is not iterable
c = Char(); Undead(c); Player(c)
"Undead" in c          # True
```

Cause: `transactions._needs_new_type` (TopKit/transactions.py:445) rebuilds the runtime type, which is what installs `__contains__`, only on the first tagging and for deletions, secrets, dunder Actions, a first Postcondition or public Reports. Being a Flag is not on that list. So when the first Tag was not a Flag, the host never gets `in`. `Keyword(c, "Undead")` works in either order.

*Proposed fix:* treat "the Tag is a Flag and the current runtime type does not answer `in`" as a type-level fact in `_needs_new_type`.

*Workaround here:* the Role Tags (`Player`, `NonPlayer`) and the roots `Guild`, `Gender`, `Kinship` are Flags, and a Character's Role is applied first. See `AtlasActorLudi/CharactersKit.py` (the `Role` docstring).

### 2. `Report` cannot hold a plain value any more

0.2.0a1 accepted `Report(value)`. 0.2.0a2 made `Report` a builder mark only (`@Report def X(tag)`). Factories that declare Tags from data (`type(name, bases, {"HIT_DIE": ...})`) then need a closure per value. A plain value mostly works, but a function stored as plain class data becomes an Action on the Agent.

*Proposed fix:* a documented value form, for example `Report.Of(value)`, or `Report(value)` accepted again when the argument is not a builder.

*Workaround here:* `Report_Of(value)` in `AtlasActorLudi/CharactersKit.py`, used at about 70 sites.

### 3. A Base's Preconditions do not gate a second Shape

```python
class Revelation(Tag):
    @Pre
    def Only_One_Revelation(target): ...   # "no Revelation yet"

class Wings(Revelation): pass
class Radiance(Revelation): pass

Wings(c); Radiance(c)    # applied: the Base's gate is not re-run
```

`_gate` evaluates only the Preconditions declared by the *pending* members of the Form, and the Base is already active. So "one of a kind" rules (one Species, one Heritage, one Celestial Revelation, one Unarmored Defense) cannot be declared once on the Base. Since 0.2.0a2 a failed Imprint no longer rolls back, so the old place for the rule (an Imprint that raises) leaves the second Shape behind.

*Question for upstream:* should the Preconditions visible in the composed Form (Base included) gate every call that adds a member of that Form? Or should there be an explicit "exclusive family" mark on the Base?

*Workaround here (Julio's ruling, QST-0093.11):* each Shape of an exclusive family declares a one-line gate calling `No_X_Yet`, which is `target not in <family Base>`. Done for Species, Heritage, Giant Heritage and Celestial Revelation (36 Shapes).

Each finding is filed upstream, answered or fixed, and on the next pin the matching workaround here is deleted.
